# 1.4G 内存服务器部署评估（2026-11-17 实测）

## 结论先行
**1.4G 运行内存可以部署，但只能低并发、单实例，且必须调低配置。**
默认配置下单次搜索峰值接近 500MB、稳定态约 325MB；只要并发失控或叠加系统开销，1.4G 会吃紧。按本文推荐配置调优后，峰值可压到 350-450MB，留有余量。

## 实测环境
- 本机 15.3GB 内存（非 1.4G），以下为 web2api 进程树的**实际占用**，可据此外推。
- 进程：web2api.exe (PID 37616) + rod 启动的 Chrome 进程树。

## 实测数据

| 场景 | Go 本体 | Chrome 进程数 | Chrome 工作集(WS) | Chrome 私有内存 | 备注 |
|---|---|---|---|---|---|
| 空闲（无请求） | ~23-24MB | 0 | 0 | 0 | 浏览器按需启动、空闲回收 |
| 单次搜索 | 24 -> 25MB | 5 -> 7 | 峰值 ~460MB，稳定 ~325MB | 峰值 ~250MB，稳定 ~162MB | 单次请求 |
| 4 并发搜索 | ~29MB | 7 | 峰值 ~544MB | - | 4 请求全部成功 |
| 8 并发搜索 | ~28MB | 7 | 峰值 ~555MB | - | 7 成功 / 1 失败（百度限流，非内存） |

关键观察：
1. **内存瓶颈在 Chrome，不在 Go。** Go 本体恒定 23-30MB。
2. **无代理时所有请求共享同一个 direct Chrome**（cmd/serve.go browserPoolKey），所以并发不会线性增加浏览器数量——峰值被单个 Chrome 的 5-7 个进程限制在 ~550MB。
3. **每个 Chrome 实例工作集 ~300MB、私有内存 ~160MB**；无代理单实例下这是硬下限。
4. 浏览器空闲后会被回收（idle_ttl=5m 默认），实测请求结束后进程树归零。
5. max_processes 是 LRU 池大小上限，不是并发信号量；配代理池时每个不同代理会各起一个 Chrome，那才会真正放大内存（N 个代理约 N × 300MB）。无代理时它基本不起作用。

## 对 1.4G 机器的评估

内存账（估算）：
- 系统 + 基础服务：假设 300-500MB（取决于发行版/是否带桌面）
- web2api Go 本体：~30MB
- 1 个 Chrome 实例峰值：~300-460MB 工作集
- 峰值合计：约 **650-1000MB**，1.4G 勉强够，但余量不大。

风险点：
- **并发叠加**：无代理时共享 Chrome，但并发请求会让它开更多 tab/renderer，实测 8 并发峰值 555MB；若后端还有其它服务，可能触发 OOM。
- **多代理池**：按之前建议给 sogou/360 配 2+ 代理，每个代理各起一个 Chrome，内存翻倍（2 个 Chrome 约 600-900MB 峰值）——1.4G 下最多 1 个代理。
- **RSS vs WS**：Linux 上看 RSS 更准（本测试是 Windows 工作集），实际以 RSS 为准预留 30% 余量。

## 推荐部署配置（1.4G 机器）

config.yaml 的 app 段：

    app:
      block_resources: "image,font,css,media"   # 已默认，务必保留
      max_processes: 1        # 无代理时影响不大；配代理时严格限制为 1
      idle_ttl: 1m            # 缩短空闲回收，默认 5m 太长
      timeout: 15             # 保持默认，别调高
      # head=false（headless）；leakless=false（池化复用更省内存）

部署侧：
- **单实例部署**，不要 docker-compose 起多个副本。
- 给容器/服务设内存上限 ~1.1G，留 ~300MB 给系统，避免 OOM killer 误杀。
- 入口层（nginx）限制并发到 2-4，别让 8+ 并发同时打进来。
- 若配置代理：**最多 1 个出口代理**，否则每代理一个 Chrome 会撑爆内存。
- 开启 swap（512MB-1G）作为突发缓冲。

## 什么时候需要更多内存
- 并发 > 4 且要稳定：建议 2G+。
- 每引擎独立代理池（4 个 Chrome 常驻）：建议 2-4G。
- 纯 API 高并发批量收录（20 URL × 4 引擎）：建议 4G+ 或改用 raw 模式（bing 不可用、收录判定降级，见 README）。

## 数据可信度说明
以上为 2026-11-17 在本机实测的进程占用；1.4G 机器的实际可用内存还取决于其操作系统、常驻服务、内核开销。建议上线前在目标机器上跑一次真实请求并观察 RSS 峰值确认。
